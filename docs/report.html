01What was built

A 3-tier assessment application, deployed twice — once to learn what breaks, and once to build it properly.

The Node.js pivot

The project began as a PHP/Laravel monolith, deployed by hand onto a single EC2 instance running Nginx, PHP-FPM and a self-hosted Jenkins server. That build worked, but every infrastructure lesson it produced — SSH trust, Linux memory limits, IAM roles, RDS network isolation — was really about the platform underneath the application, not about Laravel itself. The application layer was later rebuilt entirely in Node.js and Express, adopting a stateless design with direct-to-S3 uploads and secrets fetched at runtime, while the Jenkins engine, the EC2 topology, and the security posture carried forward unchanged.

What exists today: two EC2 instances in a public subnet — one running Jenkins as a dedicated build engine, one running the live Node.js application behind Nginx and PM2 — talking to a private RDS MySQL instance and an S3 bucket, with every credential fetched at runtime instead of stored anywhere in the code.

02Architecture

Two purpose-built EC2 instances, a database and a bucket neither the internet nor the application server can see without a role.

04The Jenkins → App SSH trust bridge

Without a managed deployment service, Jenkins needs its own way in.

An Ed25519 keypair was generated directly inside the jenkins system user's account on the Jenkins EC2. Its public half was appended to the App EC2's ~/.ssh/authorized_keys; its private half was loaded into Jenkins Credentials as app-ec2-ssh-key. From that point on, the pipeline can execute remote commands with no password and no human present.

05The CI/CD pipeline

Five stages, triggered by a GitHub webhook on every push to main.

Jenkinsfile · deployment stages
// 1. Checkout — pull the latest code
checkout scm

// 2. Sync — push it to the App EC2, excluding .git and node_modules
rsync -avz --exclude='.git' --exclude='node_modules' ./ app-ec2:/var/www/node-app

// 3. Install — production dependencies only, on the remote host
ssh app-ec2 "cd /var/www/node-app && npm install --production"

// 4. Configure — refresh the reverse proxy
ssh app-ec2 "sudo cp nginx.conf /etc/nginx/sites-available/ && sudo systemctl reload nginx"

// 5. Restart — zero-downtime reload, falling back to a cold start
ssh app-ec2 "pm2 reload node-app || pm2 start server.js --name node-app"

pm2 reload rather than pm2 restart is deliberate — reload keeps the previous process serving traffic until the new one is confirmed up, so a deployment never produces a visible gap in availability.

Because no user data ever touches the App EC2's local disk, the instance itself is disposable — it could be terminated and replaced without losing anything a user uploaded.

07Problems hit, and how they were fixed

Everything below marked current shaped the infrastructure exactly as it stands today. Everything marked retired was real, and was solved, but belonged to the Laravel prototype the Node.js pivot later replaced — kept here because the infrastructure lesson still holds even though the specific fix no longer applies.

1. Windows refused to use the downloaded SSH keycurrent

Cause

Windows downloads a .pem file with inherited permissions that other local accounts can read. SSH treats a world-readable private key as a security risk and refuses to use it.

Fix

icacls, run in PowerShell, stripped the inherited permissions and granted explicit read-only access to the current user only — satisfying SSH's requirement.

2. Processes crashed randomly under memory pressurecurrent

Cause

A t3.micro instance has 1 GB of RAM. Running Nginx, a database client, and a full JVM-based Jenkins install simultaneously exceeded it, triggering Linux's OOM killer.

Fix

A 2 GB swap file was carved out of the instance's SSD:

Swap file setup
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

Effective memory rose to 3 GB (1 physical + 2 virtual), and the random crashes stopped permanently.

3. Jenkins wouldn't install, then wouldn't startcurrent

Cause (install)

NO_PUBKEY 7198F4B714ABFC68 — the server didn't trust Jenkins's package signature yet.

Fix (install)

Downloaded Jenkins's GPG key directly and registered it at /usr/share/keyrings/jenkins-keyring.asc.

Cause (startup)

journalctl -xeu jenkins.service revealed a fatal JVM error: the installed Jenkins version requires Java 21, and the server had an older JDK.

Fix (startup)

Installed openjdk-21-jre, forced it as the active runtime with update-alternatives --config java, then cleared systemd's failure lock with systemctl reset-failed jenkins before starting it successfully.

4. Jenkins couldn't touch the files it needed to deploycurrent

Cause

The jenkins Linux user has no permission to write into /var/www or run systemctl — exactly the two things the deployment stage needs to do.

Fix

A sudoers rule was added at /etc/sudoers.d/jenkins:

/etc/sudoers.d/jenkins
jenkins ALL=(ALL) NOPASSWD: ALL

This is what allows the pipeline to restart Nginx and change file ownership without a human ever typing a password.

5. The database had to be reachable without being exposedcurrent

Fix

RDS was created with public access explicitly disabled, then a dedicated security group was opened on port 3306 with its source set to the App EC2's own security group — not an IP range. Only that specific instance can ever reach the database.

6. The current Node.js app returned 502 Bad Gateway on first deploycurrent

Diagnosis

pm2 logs showed the app had successfully fetched its secrets from Secrets Manager, but then failed with Unknown database 'assessment_db'.

Fix

Connected to the RDS endpoint directly with the mysql CLI and created the missing schema by hand. A pm2 restart node-app afterward brought the application fully online.

7. (Retired) The Laravel prototype rejected the server's PHP versionsuperseded by the Node pivot

Cause

Laravel required PHP 8.3; Ubuntu 24.04 shipped PHP 8.2 by default, so composer install failed outright.

Fix at the time

Added the ppa:ondrej/php repository, installed php8.3-fpm, and repointed Nginx's fastcgi_pass at the new socket. The lesson — that a language runtime's version can silently mismatch what a framework demands — is exactly why the Node.js rebuild pinned its own runtime version explicitly from day one.

8. (Retired) The Laravel prototype's S3 driver was missingsuperseded by the Node pivot

Cause

Class "League\Flysystem\AwsS3V3\PortableVisibilityConverter" not found — the IAM role and bucket were both configured correctly, but the PHP package that actually speaks S3's protocol had never been installed.

Fix at the time

Installed league/flysystem-aws-s3-v3 via Composer and committed the updated lockfile so the fix survived the next Jenkins deployment. In the Node.js rewrite, the equivalent dependency — the AWS SDK's S3 client — is a first-class part of the stack from the start.

08Questions worth knowing the answer to

Why pivot from Laravel to Node.js instead of just fixing the PHP version mismatch?

The PHP mismatch was fixable, and was fixed. The pivot was about the application's shape, not that one bug — a stateless Node.js service that streams uploads straight to S3 and fetches secrets at boot maps more directly onto a self-hosted, horizontally scalable deployment than a traditional PHP-FPM monolith does.

Why does the RDS security group name the App EC2's security group as its source, rather than an IP address?

An IP address changes if the instance is replaced; the security group identity does not. Referencing the security group means the firewall rule stays correct automatically even if the App EC2 itself is terminated and relaunched.

Why does the Jenkins user need a sudoers exception at all — isn't that a security risk?

It is a real trade-off, made deliberately: full automation requires Jenkins to restart services and change file ownership without a human approving each action. The risk is contained by keeping SSH access to the Jenkins EC2 itself tightly restricted, since that account is effectively as privileged as root on the App EC2.

Why buffer uploads in memory with multer instead of writing them to disk first?

Writing to local disk first would make the App EC2 stateful — a crash or replacement mid-upload could lose the file, and the instance couldn't be freely swapped out. Streaming straight from memory to S3 means the EC2 never holds a piece of user data that only exists in one place.

What would happen if the IAM role were removed from the App EC2?

Every Secrets Manager and S3 call the application makes would start failing with an authorization error, immediately and loudly — there is no hardcoded credential anywhere to silently fall back on, which is exactly the point of using a role instead of access keys.
